## Week 1, Milestone 1.1 — Voice loop skeleton (2026-07-23)

**Built:**
- `voice/stt.py` — thin wrapper around faster-whisper (`small`, CPU, int8, language auto-detect). `transcribe(audio_bytes) -> (text, language)`.
- `voice/tts.py` — thin wrapper around Piper's Python API (`PiperVoice`, loaded once and reused across calls — see Milestone 1.3 for why loading became lazy instead of at-import). `synthesize(text) -> wav_bytes`. (Originally shelled out to the Piper CLI per call like the Week 0 check script — see the perf fix below for why that changed.)
- `agent/llm.py` — provider-agnostic client: a single `requests.post` to `{LLM_BASE_URL}/chat/completions` with a fixed shopping-assistant system prompt. No SDK, no tool-calling yet (that's Week 2).
- `agent/main.py` — FastAPI app, one endpoint `POST /converse`: audio upload → STT → LLM → TTS → JSON response (`transcript`, `language`, `reply_text`, `reply_audio_base64`). `GET /` serves `agent/static/index.html`.
- `agent/static/index.html` — minimal record-button page (MediaRecorder, webm/opus), plays back the base64 WAV reply.

**Key decisions:**
- Audio in is webm/opus (browser's native `MediaRecorder` format); faster-whisper decodes it directly via PyAV, so no client-side transcoding needed. Audio out is WAV, returned base64-encoded inside the JSON body rather than as a separate binary response — keeps the endpoint single-shot and easy to test with curl.
- No session/conversation memory yet — each `/converse` call is a single independent turn. That's explicitly Milestone 1.2.
- No pytest suite yet — this session was scoped to the skeleton only (Milestone 1.3 covers mocked tests + latency logging). Verified instead with a manual end-to-end smoke test (curl + a real browser mic recording): posted/spoke, confirmed transcript → Groq reply → synthesized audio all round-tripped.
- Record button is click-to-start/click-to-stop, not press-and-hold — changed after owner testing found holding a button while framing a sentence awkward.

**Perf fix (owner-reported latency):** first end-to-end test came in at ~10.3s per turn, which felt too slow. Profiled each stage in isolation and found `voice/tts.py` was the dominant cost — it shelled out to `python -m piper` per request, respawning a process and reloading the ONNX model every single call. Switched to Piper's Python API (`PiperVoice.load` once at import time, `synthesize_wav` reused per call) — TTS dropped from ~9s to ~0.6s, total to ~7s. Remaining ~5s is faster-whisper `small` on CPU transcribing a ~5s clip; tried `beam_size=1` (greedy decoding) and raising `cpu_threads`, neither moved the needle meaningfully. Didn't drop to a smaller Whisper model to chase more speed — CLAUDE.md explicitly locks `small`/CPU as a decision made for accuracy (matters for the Hinglish stretch goal), so that tradeoff needs a conscious discussion, not a silent downgrade. If this becomes a real blocker, the actual fix is Week 3's streaming STT (hides latency instead of removing it) or explicitly renegotiating the model-size decision.

**Review:**
- Run `uvicorn agent.main:app --reload`, open `http://127.0.0.1:8000/`, click to record, talk, click to stop — this was tested live in-browser already, but re-confirm on your machine.
- Be able to explain: why turn-based before streaming (simpler to get end-to-end correct first, no VAD/barge-in complexity yet), why `requests` instead of an LLM SDK (keeps the provider swap trivial and the HTTP call fully visible), why audio comes back as base64-in-JSON instead of a raw audio response, and the TTS latency root-cause (process-per-request vs. loading the model once).

## Week 1, Milestone 1.2 — Session state (2026-07-23)

**Built:**
- `agent/session.py` — in-memory store: a plain `dict[session_id, list[{"role", "content"}]]`. `new_session_id()`, `get_history(session_id)`, `append(session_id, role, content)`.
- `agent/llm.py`'s `reply()` now takes `(history, user_text)` and splices `history` between the system prompt and the current turn.
- `agent/main.py`'s `/converse` accepts an optional `session_id` form field, mints one (`uuid4().hex`) if absent, always returns it, and appends both sides of each turn to that session's history.
- `agent/static/index.html` tracks `session_id` in a JS variable across turns and now appends every turn to a running transcript in the page instead of overwriting the last one.

**Key decisions:**
- Plain dict, no TTL/eviction — matches CLAUDE.md's "no database until needed." Fine for a single-process local demo; will need addressing before any real deployment (sessions currently live and die with the process, memory grows unbounded for long-running processes).
- Session ends when the browser tab reloads (the JS variable resets), not via any explicit "new conversation" button — kept minimal since that's enough to demonstrate both continuity and isolation.

**Verified:** via curl, told the agent "my name is Varshini and I want to buy some milk," then in the same session asked "what did I just say I wanted to buy?" — reply correctly included "milk" and "Varshini." Repeating the second question with no `session_id` (a fresh session) correctly produced a reply with no memory of the milk mention. Also confirmed live in-browser by the owner.

**Review:**
- Be able to explain: why a dict instead of Postgres at this stage, why session_id is client-supplied rather than cookie-based (keeps curl/testing trivial, no cookie/CORS complexity yet), and the memory-growth caveat above (relevant when we get to Week 4 deployment).

## Week 1, Milestone 1.3 — Tests + latency logging (2026-07-23)

**Built:**
- `tests/conftest.py` — `FakePipeline` fixture monkeypatches `voice.stt.transcribe`, `agent.llm.reply`, `voice.tts.synthesize` module-level, and clears `agent.session._sessions` before each test.
- `tests/test_converse.py` — 5 tests: response shape, a fresh `session_id` minted when absent, history correctly threaded into the LLM across repeat calls with the same `session_id`, isolation between different `session_id`s, and the latency log line containing the expected fields without leaking raw audio bytes.
- `pytest.ini` — `pythonpath = .` so `tests/` can `from agent.main import app` and `from tests.conftest import FakePipeline` without an installed package or `__init__.py` files.
- `agent/main.py` now times STT/LLM/TTS with `time.perf_counter()` and logs one line per turn via the stdlib `logging` module: `session=... stt_ms=... llm_ms=... tts_ms=... total_ms=... transcript=... reply_text=...`.

**Key decision — the one worth defending in an interview:** `voice/stt.py` and `voice/tts.py` originally loaded their models (Whisper, Piper) at *import* time. That's fine for a running server (load once, serve fast) but wrong for tests: importing `agent.main` transitively imports both wrapper modules, so every test run would eat the real ~6s model-load cost even though the tests mock `transcribe`/`synthesize` and never touch the real models — and CI wouldn't even have the gitignored Piper `.onnx` file to load. Fixed by making both loads *lazy* (load on first real call, memoized after). Tests now run in ~0.05s. Tradeoff: the first real `/converse` call after server startup now pays that load cost instead of it happening at startup — measured `tts_ms≈1900` on the first call after a fresh start vs `≈200` on every call after. Acceptable for a local demo; worth another look if this ever becomes a warm, always-on prod service (e.g. a startup event that forces the load proactively).

**Latency numbers (for the resume/interview):** stt_ms≈5000 (faster-whisper `small`, CPU — the dominant cost, expected), llm_ms≈550 (Groq), tts_ms≈200 warm / ≈1900 cold-start. Total per turn ≈6-7s warm.

**Review:**
- Run `pytest` — should be 5 passed in well under a second, no network/model access.
- Be able to explain: why STT dominates and what the fix path is (Week 3 streaming hides it, or a smaller model trades accuracy for speed), why models had to become lazy-loaded for tests to be fast/possible at all, and what's *not* logged and why (no raw audio, no API keys, per CLAUDE.md's observability rule).

## Week 2, Milestone 2.1 — MCP commerce server (2026-07-23)

**Built:**
- `mcp_commerce/shopify_client.py` — the only module that speaks to Shopify. Wraps the Storefront GraphQL API: `search_products`, `create_cart`, `get_cart`, `add_line`, `remove_line`. Raises `ShopifyError` on GraphQL errors, mutation `userErrors`, or request failures — the one exception type the rest of mcp_commerce needs to catch.
- `mcp_commerce/carts.py` — plain `dict[session_id, shopify_cart_id]`, same "no DB" pattern as `agent/session.py`.
- `mcp_commerce/models.py` — pydantic result models (`SearchProductsResult`, `CartResult`, `CheckoutResult`), every one carrying an `error: str | None` field.
- `mcp_commerce/server.py` — a `FastMCP` server (official `mcp` SDK) exposing 5 tools: `search_products`, `get_cart`, `add_to_cart`, `remove_from_cart`, `checkout`. Runs standalone via `python -m mcp_commerce.server` (stdio transport).
- `tests/test_mcp_commerce.py` — 10 tests, mocking `shopify_client` entirely, covering structured errors, the checkout confirm-gate, empty-cart rejection, and add/remove/get cart shapes.

**Blocker found and fixed (external system, not code):** the Storefront API returned zero products for every query, even though the Week 0 seed script had created 31 of them. Root cause: the custom Shopify app's Admin API token didn't have `read_publications`/`write_publications` scope, so there was no way via the API to check or fix which sales channel the products were published to. This wasn't something I could resolve by writing code — the owner had to go into the Shopify Partner Dashboard, add the scopes to the custom app's configuration, and regenerate the Admin API token. After that, all 31 grocery products (44 total, including a handful of Shopify's own default sample products) were confirmed published to "Online Store," and Storefront search started working immediately — no further fix needed, so it really was a token-scope gap, not a Storefront-visibility bug on our side.

**Key decisions:**
- `product_id` everywhere in the tool contracts is actually a Shopify **variant** GID, not a product GID. Since every seeded product has exactly one variant, there's no meaningful product/variant distinction to expose to the agent — keeping the tool contract to a single `product_id` is simpler and the agent never needs to know Shopify's data model has two levels here.
- `checkout(session, confirm=False)` — confirm defaults to `False` and returns a structured error ("ask the user to confirm first") rather than proceeding. This is a safety gate at the tool layer itself, independent of whatever the agent decides to do — Milestone 2.2 (tool-calling agent) is responsible for only ever passing `confirm=True` after the user has explicitly said yes, but even if the agent got that wrong, the tool won't finalize checkout without it.
- "Checkout" here means: validate the cart isn't empty, then return Shopify's real hosted `checkoutUrl` and a subtotal — it does **not** complete payment. That's what CLAUDE.md's "test-mode checkout only" means in practice: we prove the whole pipeline can reach a real, valid Shopify checkout link without ever touching payment.
- Transport is stdio (`mcp.run()` default), matching how most local MCP servers run (e.g. Claude Desktop's config). The agent doesn't talk to this server yet — that wiring is explicitly Milestone 2.2, so 2.1 was scoped to "the server works correctly on its own," verified via a standalone MCP client script, not via the agent.

**Verified:** `pytest` (10 mocked unit tests) plus a one-off manual script (not committed — a dev-only smoke test, similar in spirit to the Week 1 curl checks) that opened a real MCP `ClientSession` over stdio against the running server and exercised the full flow against the live Shopify dev store: searched "milk" and got all 3 brands back (Amul/Nandini/Mother Dairy — confirming the deliberate Week 0 ambiguity design actually works end-to-end), added 2x Amul milk, fetched the cart, called checkout without confirm (correctly got a structured error), called it again with `confirm=True` (got back a real Shopify `checkoutUrl`), removed the item, and confirmed removing it again correctly errors since it's no longer in the cart.

**Review:**
- Be able to explain: why Shopify-specific code lives only in `shopify_client.py` (swappable backend — replacing Shopify with ONDC later would mean rewriting that one file, not `server.py`'s tool contracts), why `product_id` is secretly a variant ID, why `checkout` needs a confirm flag at the tool layer *in addition to* agent-level confirmation logic, and the publications-scope story above (it's a good example of "the bug was in account configuration, not code").

## Week 2, Milestone 2.2 — Tool-calling agent loop (2026-07-23)

**Built:**
- `agent/mcp_client.py` — `MCPClient`: connects to `mcp_commerce.server` over stdio (spawned once at app startup via a FastAPI `lifespan`, not per-request), fetches the tool list once via `list_tools()` and converts it to the OpenAI function-calling schema shape. `call_tool()` normalizes both mcp_commerce's own structured `error` results and MCP-protocol-level errors (bad arguments, unknown tool — confirmed these come back as `CallToolResult(isError=True)` rather than raising) into the same `{"error": ...}` shape.
- `agent/llm.py` — `reply()` is gone, replaced with `chat_completion(messages, tools=None)`, a thin pass-through to the chat/completions endpoint that returns the raw assistant message (may contain `tool_calls`). Still fully provider-agnostic; still no domain/system-prompt content in this file.
- `agent/agent_loop.py` — new module, the actual "decide what to do" logic. `run_turn(session_id, user_text, mcp_client)` loops: call the LLM with tool schemas, execute any `tool_calls` via the MCP client, feed results back as `role: "tool"` messages, repeat until a plain-text reply or `MAX_TOOL_ROUNDS=6` rounds are used up (safety cap against a confused model looping forever in one request). The system prompt here is where all the CLAUDE.md agent-behavior requirements actually live: ask before guessing an ambiguous brand, convert casual quantity phrases to the product's listed unit, never call `checkout(confirm=true)` without explicit user confirmation in the conversation, retry a failed tool call once with corrected arguments or explain the problem in plain language.
- `agent/session.py` — `append()` now takes a full message dict instead of `(role, content)`, since tool-calling messages carry `tool_calls`/`tool_call_id` that a two-field shape can't hold. This means the LLM sees the *entire* history of what tools were called and what they returned in past turns, not just the user-visible text — that's what makes "remove the bread" work without re-specifying which bread, per CLAUDE.md's session-memory requirement.
- `agent/main.py` — added a `lifespan` context manager to own the MCP client's connect/close lifecycle; `/converse` now calls `agent_loop.run_turn()` instead of `llm.reply()`. Latency log field renamed `llm_ms` → `agent_ms` since it now covers however many LLM+tool round trips a turn takes, not one call.

**Key decisions:**
- Confirmation-before-checkout and ambiguity clarification are **prompt-driven, not hardcoded**. There's no Python `if` statement checking for brand ambiguity or a "has the user confirmed?" state flag — the system prompt instructs the model to behave this way, and Milestone 2.1's tool-layer `confirm=False` default is the structural backstop that holds even if the prompt instruction ever fails. This matches "prefer simple, explicit code over clever abstractions" — the alternative (a hand-rolled dialogue state machine) would be far more code for behavior an instruction-following model already does well, and it's exactly the kind of thing Milestone 2.3's eval suite exists to hold accountable with real pass/fail numbers instead of vibes.
- `MAX_TOOL_ROUNDS = 6` is a code-level safety cap, separate from the prompt's "retry once" instruction. The prompt asks the model to retry a failed tool call at most once before explaining the problem; the round cap is just a hard backstop against an actual infinite loop bug, not the mechanism enforcing "once."

**Verified:**
- `pytest`: `tests/test_agent_loop.py` (4 tests — plain reply, single tool-call round-trip with correct `tool_call_id` threading, history correctly carrying across two calls to `run_turn`, and the round cap actually halting an LLM that never stops calling tools) plus `tests/test_converse.py` updated to treat `agent_loop.run_turn` as a mocked black box.
- Manual, against the live Groq + Shopify dev store (no mocks): a multi-turn conversation — "add two packets of milk" → correctly asked "Amul, Nandini, or Mother Dairy?" instead of guessing; naming a brand → correctly resolved and added; adding bread too, then asking "what's in my cart" → correct running total; "check out my order" → read back the cart and total and asked for confirmation, did **not** call `checkout(confirm=true)`; only "yes, I confirm" triggered the real checkout call and returned an actual Shopify checkout URL.
- Along the way found (not a code bug): faster-whisper kept mis-hearing "Amul" as "Emil" — an Indian brand name outside its English-biased vocabulary. The agent's response to that was actually correct (recognized "Emil" isn't a real brand, asked again) rather than silently adding the wrong thing, but it's a genuine STT accuracy limitation to keep in mind for Week 3's Hinglish work.
- **Not** exhaustively verified by hand: the specific "retry with corrected arguments" path, and quantity/unit phrasing like "half a dozen eggs." Both need many scenarios to check properly rather than a handful of live conversations — that's precisely what Milestone 2.3 is for.

**Review:**
- Be able to explain: why agent behavior lives in a system prompt rather than Python control flow, why there are two independent layers enforcing the checkout-confirmation rule (prompt + tool default) and why that's not redundant, why session history now stores raw message dicts instead of just text, and the Amul/Emil STT story as a concrete example of an accuracy limitation that a code fix can't solve.

## Week 2, Milestone 2.3 — Evals v1 (2026-07-25)

**Built:**
- `evals/fake_shopify.py` — in-memory catalog + cart backend, same function signatures as `mcp_commerce.shopify_client`, so `mcp_commerce/server.py`'s real tool functions run completely unmodified against it.
- `evals/fake_mcp_client.py` — in-process fake MCP client (no subprocess): patches both `mcp_commerce.server.shopify` and `mcp_commerce.carts.shopify` (both modules import `shopify_client` under their own local alias, so both needed patching), and calls the real tool functions directly via `mcp_commerce.server.mcp.list_tools()`.
- `evals/scenarios/*.yaml` — 20 scenarios: happy paths, quantity edge cases (dozen/half-dozen eggs, kg conversions), brand/type ambiguity (milk, bread, dal, biscuits), the checkout-confirmation trap, session memory, multi-turn cart building, error handling.
- `evals/runner.py` — loads YAML scenarios, runs each through the real `agent_loop.run_turn`, scores per-turn (`expect_tools`/`forbid_tools`/`expect_clarification`/`forbid_confirmed_checkout`/`expect_confirmed_checkout`) and scenario-level (`expected_final_cart`), prints a pass-rate report. Proactively throttles LLM calls 3 seconds apart (`evals/runner.py`'s `_throttled_chat_completion`) since a tool-calling eval run fires many requests back-to-back, unlike normal interactive use.
- `tests/test_evals.py` — parametrizes pytest over all 20 scenario files, one test per scenario. Marked `@pytest.mark.eval` and excluded from the default `pytest` run via `pytest.ini`'s `addopts = -m "not eval"`, since these hit the live LLM and are slow/quota-consuming, unlike every other test in this project. Run explicitly with `pytest -m eval`, or use `python -m evals.runner` for the human-readable pass-rate report.

**Final result: 20/20 scenarios passing (100%)** against live Groq (`llama-3.3-70b-versatile`), with Shopify mocked per CLAUDE.md's evals spec.

**Real bugs found and fixed (not just eval-writing):**
1. **Session-id leakage.** The LLM was inventing placeholder `session` values (e.g. `"current_session"`) for tool calls because `session` was exposed as a normal LLM-fillable parameter in the tool schema — the model has no way to know the real session_id and shouldn't be asked to guess it. Fixed by stripping `session` from the OpenAI-format tool schemas the LLM sees (`build_tool_schemas()` in `agent/mcp_client.py`, which now also returns a `tools_requiring_session` set) and having `agent_loop.run_turn` auto-inject the real `session_id` into arguments for any tool in that set.
2. **Half-a-dozen-eggs quantity bug.** For "Add half a dozen eggs," the agent added quantity=6 of "Eggs 6pc Tray" instead of quantity=1 — it wasn't reliably treating the tray as the unit despite the existing quantity instruction. Fixed with a tightened, concrete worked example in the system prompt.
3. **Bread brand ambiguity.** Asked to add "one bread" with three brands in the catalog, the agent silently re-searched with a narrower query ("white bread") instead of asking, added that guess, then on the user's follow-up brand answer treated it as an *additional* item rather than resolving the same request — leaving two breads in the cart. Fixed with explicit prompt guidance: don't guess by re-searching, always ask; and a follow-up answer to your own clarifying question resolves that same request, don't also keep an earlier guess.
4. **Checkout-on-empty-cart.** "Check out my order." as the very first message triggered `checkout(confirm=true)` immediately, with no prior confirmation exchange — this rule was already being followed correctly when the cart had an item first (see Milestone 2.2's verified checkout-confirmation-trap conversation), it just didn't hold on an empty first-turn cart. Fixed with explicit prompt guidance that the rule applies "even on the first message, even if the cart is empty," and that `checkout` should never be called before `get_cart` has been checked first.
5. **LLM reliability bug in `agent/llm.py`.** Groq/Llama-3.3-70b occasionally emits a malformed non-JSON function-call token (`<function=name{"arg": "val"}>`) instead of a proper `tool_calls` response, surfaced by Groq as a 400 error with `code: "tool_use_failed"`. Diagnosed by capturing the exact failing request payload and replaying it directly against the API: the same payload sometimes failed 5/5 identical retries in a row (looks deterministic in the moment), but the *same* payload succeeded when replayed at a later point in time, and a temperature bump (0→0.3) broke a request out of the bad pattern in one direct test — so it's inference-level noise, not a fixed function of the prompt. Added a bounded retry in `agent/llm.py` specifically for this error code that nudges `temperature` up on each retry (alongside the pre-existing 429 rate-limit retry), instead of crashing the whole turn.

**One eval design correction, not a bug:** `remove_item_not_in_cart` originally asserted `remove_from_cart` must be called even for "remove the toothpaste" when toothpaste was never added. The agent instead called `get_cart`, saw no toothpaste in the cart lines, and answered correctly — it never had a `product_id` to pass into `remove_from_cart` in the first place (there's nothing in the cart to remove, and toothpaste isn't even a catalog item). Rewrote the scenario to `forbid_tools: [remove_from_cart]` and made the intended flow explicit in the system prompt: for removals, search first to identify the product, check the cart for a matching `product_id`, remove it if present, otherwise tell the user it isn't there — don't call `remove_from_cart` for something that was never added.

**Notable friction, not a bug:** Groq's free-tier daily token quota (100k TPD) was hit and recovered (it's a rolling window, not a hard once-a-day reset) twice during this milestone — once mid-session on 2026-07-23 (blocked the first full run), once again during fix verification on 2026-07-25. Worked around by conserving quota (checking rate-limit headers before big runs, batching only the scenarios that still needed a result instead of re-running all 20 every time) rather than by creating additional Groq accounts, which would violate Groq's terms of service around quota circumvention — a real constraint of building on a free tier that's worth being upfront about in an interview.

**Review:**
- Be able to explain: why Shopify is mocked but the LLM isn't (evals validate *agent* behavior, not the commerce backend, and CLAUDE.md scopes it that way), why `evals/fake_mcp_client.py` calls the real tool functions in-process instead of spawning a subprocess, why `tests/test_evals.py` is marked and excluded from the default `pytest` run instead of just being another test file, the session-id leakage bug and why tool schemas shouldn't expose parameters the LLM can't actually know, and the malformed-tool-call story — the difference between "deterministic bug" and "inference noise that looks deterministic in a short window," and why the fix is a temperature-varying retry rather than a fixed backoff.

## Week 3, Milestone 3.1 — Streaming STT over WebSocket (2026-07-25)

**Built:**
- `voice/vad.py` — `Endpointer`, a small state machine wrapping `webrtcvad` (installed as `webrtcvad-wheels`, a prebuilt-wheel fork — plain `webrtcvad` fails to build on Windows without MSVC build tools). Fed one fixed-size PCM frame (30ms @ 16kHz, `FRAME_BYTES=960`) at a time; tracks consecutive speech/silence frames and returns the finalized utterance's PCM bytes once `END_SILENCE_FRAMES` (~750ms) of trailing silence follows a confirmed `START_SPEECH_FRAMES` (~90ms) of speech. `vad` is an injectable field (`VoiceActivityDetector` protocol) so tests drive it with a scripted fake instead of real audio.
- `voice/pcm.py` — `pcm16_to_wav()`: wraps raw PCM in a minimal WAV header via the stdlib `wave` module. Needed because `voice/stt.py` decodes through PyAV, which requires a container/header — it can't take headerless PCM directly.
- `agent/ws_stream.py` — `handle_stream()`: the WebSocket-side pipeline. Accepts binary PCM frames, feeds them to an `Endpointer`, and on each finalized utterance runs the same `stt.transcribe -> agent_loop.run_turn -> tts.synthesize` sequence `/converse` uses, then sends one `{"type": "turn", ...}` JSON message back. One connection carries many turns — the endpointer resets after each finalized utterance and keeps listening, so the user doesn't reconnect between turns. A `{"type": "stop"}` text message or client disconnect ends the loop.
- `agent/main.py` — new `@app.websocket("/converse/stream")` route (accepts an optional `session_id` query param, same minting behavior as `/converse`) and a `GET /stream` route serving the new demo page. **The original `POST /converse` endpoint is untouched** — see decision below.
- `agent/static/stream.html` — new demo page: one "Start/Stop streaming" button. Captures the mic via `AudioContext` + `ScriptProcessorNode` (deprecated in favor of `AudioWorklet`, but needs no separate module file — kept for demo simplicity, noted in-code as the thing a production version would swap out), does simple nearest-sample downsampling from the browser's native rate (typically 44.1/48kHz) to 16kHz mono int16, and streams 960-byte frames over the WebSocket continuously — no per-utterance button press.

**Key decisions:**
- **Kept `POST /converse` alongside the new WebSocket endpoint instead of replacing it**, even though the milestone text says "switch." The old endpoint is simple, already has full test coverage (`tests/test_converse.py`), and is still the easiest path for one-shot/non-browser callers (e.g. a curl smoke test). Removing it would have bought nothing this milestone and cost test coverage and a fallback demo path. Treat this as an explicit scope call, not an oversight — worth mentioning if asked why both exist.
- **"Incremental transcription" = VAD end-pointing, not live partial captions.** faster-whisper has no true streaming/incremental decode mode. The alternative (re-running whisper every ~1-2s on the growing buffer to show live partial text) would burn CPU re-transcribing overlapping audio and add real latency-management complexity for a portfolio project, for a "live captions" effect that isn't actually needed anywhere else in the system — Milestone 3.2's barge-in needs a clean utterance boundary anyway, which end-pointing already gives it. Chose the simpler option deliberately (owner confirmed) rather than defaulting to the more impressive-looking one.
- **`webrtcvad` over `silero-vad`.** webrtcvad is a tiny, fast, dependency-light C library; silero-vad is a neural VAD (more accurate on noisy audio) but pulls in torch, which nothing else in this codebase needs. ## Week 3, Milestone 3.2 — Barge-in (2026-08-17)

**Built:**
- `voice/vad.py` — `Endpointer` gained two public properties: `in_speech` (flips true after ~90ms of speech, fast but noise-prone) and `speech_confirmed` (true only once `MIN_SPEECH_FRAMES` of real speech has accumulated — reusing the same threshold that fixed Milestone 3.1's hallucination bug, rather than inventing a new one).
- `agent/ws_stream.py` — sends `{"type": "speech_started"}` on `speech_confirmed`'s False->True transition, well before the utterance finishes. Each finalized utterance's turn now runs as its own `asyncio.Task` (tracked in a small `_TurnState` dataclass) instead of a bare `await`, so a `{"type": "barge_in"}` client message can cancel just the currently-running turn and drain the pending-utterance queue, without killing the background consumer loop that keeps listening for what comes next.
- `agent/static/stream.html` — tracks whether reply audio is actively playing (`ended`/`pause` listeners plus a flag set on successful `.play()`); on `speech_started`, only sends `barge_in` and stops playback if audio is genuinely playing right then. Also added explicit `echoCancellation`/`noiseSuppression`/`autoGainControl` constraints to the `getUserMedia` call, and an on-page note recommending headphones.
- `voice/stt.py` — added a confidence-gated retry: if `info.language_probability < 0.6` and the detected language isn't already English, retranscribe once with English forced.

**Key decisions / real bugs found live, in order:**
1. **First version sent `barge_in` unconditionally on every `speech_started`, not just during playback.** Since a full turn takes 5-15s, any utterance started before the prior one finished computing — completely normal back-to-back conversation — got its prior turn cancelled. Result: nothing ever got a reply, and the server log showed repeated STT completions with zero matching turn-completion or error lines (cancellation is silently swallowed by design). Looked exactly like a hung/quota-exhausted LLM from the outside; it wasn't. Fixed by gating the client's `barge_in` send behind "is audio actually playing" — matching the milestone's literal spec ("if the user speaks *while TTS audio is playing*").
2. **Raw `in_speech` (~90ms) was too trigger-happy for real background noise/echo**, so `speech_confirmed` (reusing `MIN_SPEECH_FRAMES`, ~300ms) became the actual barge-in trigger instead.
3. **Acoustic echo: the reply's own voice, played through speakers, got picked up by the mic and mistaken for the user interrupting**, after just a word or two. Important distinction from bug 2: no speech-duration threshold can fix genuine echo, since it's real, continuous, natural speech-shaped audio — raising the threshold further only delays the false trigger while equally delaying real interruptions. Mitigated (not fully solved) with browser-level echo-cancellation constraints and a headphones recommendation on the page. Full AEC for arbitrary local `<audio>` playback (vs. WebRTC call audio, where it's most reliable) is a genuinely hard problem without dedicated hardware — this is an honest, explainable limitation, not a claimed fix.
4. **Unrelated to barge-in mechanics, found the same session: the first utterance came back entirely in Devanagari script** — clear English misdetected as Hindi by Whisper's language auto-detect. Root cause: `info.language_probability` was never checked. Auto-detect stays on (needed for Hinglish per CLAUDE.md), but a confidence-gated retry (force English only when detection was already unsure, and not already English) catches this specific failure mode without second-guessing genuinely confident non-English detections.
5. Cancelling an `asyncio.Task` only stops our own code from awaiting the result — a blocking call already dispatched to a thread (the LLM HTTP call via `asyncio.to_thread`, or a Shopify tool call inside it) keeps running regardless, since threads can't be forcibly killed. If a cancelled turn had already called `add_to_cart`, that mutation still applies for real. Accepted as an inherent tradeoff of using threads for blocking I/O — not dangerous (nothing irreversible; `checkout` has its own separate confirm gate) but worth being able to explain.

**Verified:**
- `tests/test_vad.py`: 4 new tests (`in_speech` and `speech_confirmed` transition timing, including that a brief noise blip never confirms).
- `tests/test_ws_stream.py`: 2 existing tests updated for the new `speech_started` message; added `test_barge_in_cancels_in_flight_turn_and_drops_queued_utterance` (a `threading.Event`-gated fake `run_turn` proves a cancelled turn produces no reply, a queued utterance never reaches `run_turn` at all, and a subsequent utterance still processes normally afterward).
- `tests/test_stt.py`: 4 new tests for the language-confidence retry (retries only when unsure and non-English; leaves confident non-English and already-English detections alone).
- Full suite: 52 tests passing.
- **Live end-to-end verification by the owner** in the browser with a real mic: a full multi-turn conversation through search, brand clarification, add-to-cart, and checkout, with genuine barge-in interruption working correctly and no further false triggers after the echo-cancellation and language-retry fixes.

**Review:**
- Be able to explain: why the milestone's literal spec ("while TTS audio is playing") is the load-bearing qualifier — the same `speech_started` signal without that gate cancels *every* turn, not just genuine interruptions; why `speech_confirmed` exists separately from `in_speech` (early-but-noisy vs. slower-but-trustworthy, and why a false positive is worse for barge-in than for ordinary utterance buffering); why acoustic echo is a fundamentally different problem from a noise blip (continuous real speech vs. a brief non-speech burst) and can't be fixed by the same duration-threshold trick; and the asyncio-cancellation-vs-thread limitation (cancelling a task doesn't stop a blocking call already handed to a thread).

**Update — resolved same day, two real bugs found by the actual docker build:**

Docker Desktop got installed and the real build/run cycle immediately surfaced what the clean-venv check structurally couldn't catch:

1. **Unpinned `mcp` dependency.** Build log showed pip installing `mcp==2.0.0` fresh; the local `.venv` (set up weeks ago, never reinstalled) has `mcp==1.28.1`. Version 2.0.0 moved/removed `mcp.server.fastmcp`, so `mcp_commerce/server.py`'s `from mcp.server.fastmcp import FastMCP` crashed the subprocess at import time. This is a real, pre-existing latent bug in the *project's own* `requirements.txt`, not a Docker-specific issue — a fresh `pip install` on any machine today would hit it. Fixed by pinning `mcp==1.28.1` in both `requirements.txt` and `requirements-deploy.txt`.

2. **`agent/mcp_client.py` never passed `env=` when spawning the `mcp_commerce.server` subprocess.** After fixing (1), `/converse/text` returned a generic "technical issue" reply — the agent's own graceful error-recovery message, which by design doesn't leak the underlying error. Diagnosed by testing each layer directly inside the running container rather than guessing from that generic message: a raw `shopify_client.search_products()` call worked (ruling out network/credentials at the Shopify-API layer); calling the `mcp_commerce.server` tool wrapper directly also worked (ruling out the tool logic itself); only the full `MCPClient.call_tool()` stdio round-trip — the actual path `agent_loop.py` uses — failed, with `KeyError: 'SHOPIFY_STORE_DOMAIN'` surfacing from *inside the subprocess*. Root cause: the MCP SDK's `stdio_client` does not inherit the parent process's environment by default (confirmed by inspecting its source: it calls `get_default_environment()`, a minimal safelist of `PATH`/`TEMP`/etc., deliberately excluding app secrets, unless the caller explicitly passes `env=`). This bug has existed since Milestone 2.1 and was invisible for the entire project because `mcp_commerce/server.py`'s own `load_dotenv()` call always happened to find a real `.env` file on disk in every local dev environment so far, masking the fact that env vars were never actually flowing through the parent-child process boundary the way the code implicitly assumed. It broke the instant that coincidence stopped holding — a Docker image correctly (and deliberately) has no `.env` file. Fixed with one line: `StdioServerParameters(..., env=dict(os.environ))`.

After both fixes, rebuilt and ran the real container: `/health` returns 200, `POST /converse/text` genuinely adds "Tata Salt" to the real Shopify cart (live LLM + live Shopify API from inside the container), and a fresh `session_id` correctly shows an empty cart (session isolation intact). Full local suite: still 56/56 passing.

## Week 4, Milestone 4.2 — AWS deploy, text mode (2026-08-17)

**Built:** a `t3.micro`/`t2.micro` EC2 instance (Amazon Linux 2023) running the exact same `infra/Dockerfile` image from Milestone 4.1, accessed entirely through AWS Systems Manager Session Manager (browser-based terminal, IAM-authenticated) instead of SSH — the security group has zero inbound rules. Repo was pushed to GitHub for the first time this session (`d7c73e0`, previously local-only across 11 commits) so it could be `git clone`d onto the instance; built the image there directly rather than using a container registry, to keep the deploy story simple and matching exactly what was already verified locally.

**Cost-safety, done first:** an AWS Budgets "Zero spend budget" (alerts on any charge above $0.00) plus Free Tier usage alerts, set up before touching EC2 at all — tighter than `PLAN.md`'s literal "₹100 alarm" suggestion, matching the owner's actual stated goal ("I don't want to spend any money").

**A real design correction, caught before acting on it:** the first plan floated was "no public IP at all, use SSM for everything" as a cost-avoidance measure. That's wrong for this app specifically — VoiceCart's own code makes outbound calls to Groq and Shopify, which needs internet access regardless of how *we* administer the instance; SSM only solves the admin-access side. A public IPv4 is unavoidable for the app to actually function, and AWS has charged for every public IPv4 (including the default one on a running instance) since Feb 2024 (~$0.005/hr). Caught and corrected this before the owner acted on the flawed plan. The actual, honest cost-safety measure: stop the instance whenever it's not actively in use — both the compute and public-IP charges stop while stopped — with the Zero Spend Budget as a backstop for anything unexpected. SSM Session Manager was kept anyway, not for cost, but because it avoids managing SSH keys and needs no open inbound port.

**Real bugs hit during the live walkthrough (all diagnosed remotely, over chat, without ever seeing the actual AWS console directly until a screenshot was shared):**
1. **"Failed to connect to your instance"** the first time Session Manager was tried. Root cause: the newly-created IAM role (with `AmazonSSMManagedInstanceCore`) hadn't actually been attached to the instance before launch — checked via **Actions → Security → Modify IAM role**, which showed it blank. Attached it, waited a couple of minutes for the SSM agent to register, confirmed via Systems Manager → Fleet Manager showing the instance **Online** (a more reliable signal than the EC2 Connect dialog itself).
2. **"Port 22 (SSH) is not authorized"** — a red herring, not a bug: the owner was still on the **EC2 Instance Connect** tab of the Connect dialog (SSH-based), not **Session Manager**. Confirmed from a screenshot which option was actually radio-selected.
3. **`could not create work tree dir`** on `git clone` — a well-known SSM quirk: sessions often start in a directory (e.g. `/usr/bin`) the session user can't write to, unlike a normal SSH login shell that starts in `$HOME`. Fixed with `cd ~` first.
4. **A "JSON decode error... Invalid control character"** on the first `curl -X POST .../converse/text` test — not an app bug, a copy-paste artifact: the terminal line-wrapped a long `-d '{"text": "..."}'` argument and a literal newline landed inside the JSON string. Fixed by using a shorter one-line test message.

## Week 4, Milestone 4.3 — CI/CD (2026-08-18)

**Built:** `.github/workflows/ci.yml`, three jobs:
1. `lint-and-test` — `ruff check .` + `pytest` on every push (any branch) and every PR into `master`. No secrets, no external calls, fast and deterministic — this is the gate that should never be skipped.
2. `evals` — the live-Groq eval suite (`python -m evals.runner`), gated to `push` events on `master` only, not every push/PR. Pass-rate output goes to the GitHub Actions job summary. Marked `continue-on-error: true`.
3. `build-and-push` — builds `infra/Dockerfile` and pushes to GHCR (`ghcr.io/<owner>/voicecart:latest` and `:<sha>`), also `master`-only.

**Key decisions, all owner-confirmed deviations from the plan text's literal "on push → ... run evals" / "on main → build and deploy":**
- **Evals run on `master` pushes only, not every push/PR.** CLAUDE.md's evals section and this project's own history (Milestones 2.3, 3.3 — Groq free-tier 429s hit repeatedly during normal development, sometimes mid-session) make "run 20+ live-LLM-calling scenarios on every commit to every branch" a real, recurring quota risk, not a hypothetical one. Running only on `master` gets a pass-rate signal before/at merge without multiplying quota burn by every WIP push.
- **The `evals` job is `continue-on-error: true`.** This model's tool-calling has documented non-deterministic flakiness (the `tool_use_failed` pattern from Milestone 2.3, the flaky `hinglish_remove_without_respecifying_brand` scenario from 3.3) — a red CI check for a known-noisy scenario would train the owner to ignore red CI, which is worse than not gating on it at all. The report is still posted to the job summary either way, so a real regression is still visible, just not blocking.
- **CD stops at "build and push the image," not "deploy to EC2."** Milestone 4.2's EC2 deploy is on a family member's personal AWS account with no CI credentials wired up; auto-deploying from a shared GitHub Actions workflow into that account would need IAM credentials stored as repo secrets, which is a real access-control decision, not a default to fall into silently. Pulling the freshly-pushed image and restarting the container on the instance stays a manual step (`docker pull` + restart over the existing SSM session).

**Lint step surfaced 8 real, pre-existing `ruff` findings** (this project had never run a linter before): unsorted imports in `evals/fake_mcp_client.py` and `mcp_commerce/server.py`, an unnecessary `import voice.stt as stt` alias in `tests/test_stt.py`, two nested `with` statements in `tests/test_llm.py` collapsed to one each, a nested `if` in `evals/runner.py` collapsed with `and`, a bare `pytest.raises(Exception)` in `tests/test_llm.py` narrowed to the actual raised type (`requests.HTTPError`, from `agent/llm.py`'s `raise_for_status()`), and a missing explicit `check=False` on a `subprocess.run` call in the standalone `voice/tts_check.py` script. All genuine, all low-severity — fixed before committing rather than suppressing or excluding files, since none of them were false positives. `ruff` ships a fairly broad default rule set (not just pycodestyle/pyflakes) as of the installed version (0.16.3); didn't add a `pyproject.toml`/`ruff.toml` to narrow it, since the defaults turned out to be exactly right-sized for this codebase (8 real findings, zero noise) rather than either too strict or too permissive.
