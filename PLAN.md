## Week 1 — Turn-based voice pipeline

**Milestone 1.1 — Voice loop skeleton.** [x]
FastAPI app with one endpoint: POST /converse accepts an audio file, runs STT, sends transcript to the LLM with a simple system prompt (no tools yet — just a helpful shopping assistant persona), synthesizes the reply with TTS, returns audio + transcript JSON. Plus a minimal HTML page with a record button that hits this endpoint and plays the response.

Done 2026-07-23. `agent/main.py` (FastAPI, single POST /converse + static index page), `voice/stt.py` / `voice/tts.py` (thin wrappers around the Week 0 check scripts), `agent/llm.py` (plain `requests` call to the OpenAI-compatible chat/completions endpoint — no provider SDK). Smoke-tested end-to-end locally with a real WAV and live in-browser via the record button: transcript → Groq reply → synthesized audio all round-tripped correctly. No session memory yet (Milestone 1.2) and no pytest suite yet (Milestone 1.3) — this milestone was scoped to the skeleton only.

Perf fix during owner testing: initial round-trip was ~10.3s, almost entirely `voice/tts.py` shelling out to `python -m piper` per request (process spawn + ONNX model reload every call). Switched to Piper's Python API (`PiperVoice.load` once at import, `synthesize_wav` in-process) — brought total to ~7s. Remaining time is faster-whisper `small` on CPU (~5s for a ~5s clip); tried `beam_size=1` and higher `cpu_threads`, neither helped meaningfully, and swapping to a smaller Whisper model wasn't done since CLAUDE.md locks `small`/CPU as a deliberate decision (accuracy matters for Hinglish later) — that's a tradeoff to revisit together if latency becomes a real blocker, not Week 3's planned streaming-STT fix. Also swapped the record button from press-and-hold to click-to-start/click-to-stop per owner feedback (holding was awkward).

**Milestone 1.2 — Session state.** [x]
Add session_id handling and conversation history so multi-turn works ("what did I just ask?"). In-memory store.

Done 2026-07-23. `agent/session.py`: plain dict keyed by `session_id`, storing each turn's {"role", "content"}. `/converse` now accepts an optional `session_id` form field (mints one via `uuid4().hex` if absent, always returns it) and threads the session's history into `agent/llm.py`'s `reply()` before the current turn. Demo page tracks `session_id` in a JS variable and appends every turn to a running transcript instead of overwriting. Verified via curl: told the agent "my name is Varshini and I want to buy some milk," then in the same session asked "what did I just say I wanted to buy?" — got back "milk, Varshini" correctly; repeating the second question with no session_id (fresh session) correctly came back with no memory of it.

**Milestone 1.3 — Tests + latency logging.** [x]
pytest coverage for the endpoint (mock STT/LLM/TTS). Log per-stage latency (STT ms, LLM ms, TTS ms) — you'll cite these numbers later.

Done 2026-07-23. `tests/conftest.py` + `tests/test_converse.py`, 5 tests: response shape, session_id minted when absent, history correctly threaded into the LLM for repeat calls with the same session_id, isolation between different session_ids, and latency fields present in the log line without leaking raw audio bytes. All pass in ~0.05s. That speed only works because `voice/stt.py` and `voice/tts.py` were changed to load their models lazily (on first real call) instead of at import time — otherwise every test run would pay the ~6s Whisper+Piper load cost, and CI wouldn't even have the (gitignored) Piper model file available. Tradeoff: the very first real `/converse` call after server startup now eats that load cost instead of it happening at startup (measured: first call tts_ms≈1900 vs ≈200 on later calls) — acceptable for a local demo, worth knowing if this becomes a prod service. `agent/main.py` now times each stage with `time.perf_counter()` and logs one line per turn: `session=... stt_ms=... llm_ms=... tts_ms=... total_ms=... transcript=... reply_text=...` — no audio bytes or API keys logged, per CLAUDE.md. Latest real numbers: stt_ms≈5000 (dominates, expected for `small` on CPU), llm_ms≈550, tts_ms≈200-1900 depending on cold/warm.

Interview checkpoint — you should be able to explain: why turn-based first, where the latency goes, what faster-whisper's model sizes trade off.

## Week 2 — Agent + MCP commerce tools + evals

**Milestone 2.1 — MCP server.** [x]
`mcp_commerce` exposing: `search_products(query, limit)`, `add_to_cart(session, product_id, qty)`, `remove_from_cart`, `get_cart`, `checkout(confirm=true)`. Each wraps the Shopify Storefront API. Strict pydantic schemas, structured errors.

Done 2026-07-23. `mcp_commerce/shopify_client.py` (only module that talks to Shopify — GraphQL Storefront API: product search, cart create/read/add/remove), `mcp_commerce/carts.py` (in-memory `session_id -> Shopify cart_id` map), `mcp_commerce/models.py` (pydantic result schemas, every one with an `error` field), `mcp_commerce/server.py` (FastMCP server, 5 `@mcp.tool()`-decorated functions). `product_id` in every tool is the Shopify variant GID — the agent never needs to know Shopify's product/variant distinction. `checkout` defaults `confirm=False` and returns a structured error until called with `confirm=True`; the agent (Milestone 2.2) is responsible for only passing `True` after explicit user confirmation.

Blocker hit and fixed before this could start: the Storefront API returned zero results for all 31 seeded products — turned out the custom app's Admin API token was missing `read_publications`/`write_publications` scope, so there was no way to confirm/fix product-to-Online-Store-channel publication. Owner added the scopes and regenerated the token; after that, all 31 products (44 total including a few of Shopify's own sample products) were confirmed published, and Storefront search worked correctly, including returning all 3 milk brands for a "milk" query — exactly the ambiguity the Week 0 seed data was designed for.

Verified two ways: (1) `tests/test_mcp_commerce.py`, 10 tests mocking `shopify_client` — covers structured errors, the checkout confirm-gate, empty-cart rejection, add/remove/get cart shapes. (2) A one-off manual script driving a real MCP `ClientSession` over stdio against the live server (not committed — dev-only smoke test) that exercised the whole flow against the actual Shopify dev store: searched "milk" (got all 3 brands), added 2x Amul milk, fetched the cart, checkout without confirm (correctly errored), checkout with confirm=true (got back a real `checkoutUrl`), removed the item, then confirmed removing again correctly errors since it's no longer in the cart.

**Milestone 2.2 — Tool-calling agent loop.** [x]
Replace the echo agent: LLM now decides between replying, calling a tool, or asking a clarifying question. Implement confirmation-before-checkout and ambiguity clarification ("Amul or Nandini?"). Retry-once on recoverable tool errors.

Done 2026-07-23. `agent/mcp_client.py` (spawns `mcp_commerce.server` over stdio once at app startup via a FastAPI lifespan, fetches tool schemas once and converts them to OpenAI function-calling format — the MCP server's own schemas stay the single source of truth). `agent/agent_loop.py` — `run_turn(session_id, user_text, mcp_client)`: loops calling `agent/llm.py`'s new `chat_completion(messages, tools)` (replaces the old `reply()`), executing any `tool_calls` via the MCP client, feeding results back, until a plain-text reply or a `MAX_TOOL_ROUNDS=6` cap. `agent/session.py`'s history now stores full message dicts (not just role/content), since tool-calling messages carry `tool_calls`/`tool_call_id`. All agent behavior (ambiguity clarification, confirm-before-checkout, quantity/unit conversion, retry-once-then-explain on tool errors) is driven by `agent_loop.py`'s system prompt, not hardcoded Python logic — the tool layer's own `confirm=False` default (Milestone 2.1) is the structural backstop in case the prompt ever fails.

Verified two ways: (1) `tests/test_agent_loop.py` (4 tests mocking `llm.chat_completion` and a fake MCP client — plain reply, single tool-call round-trip, history carrying across turns, the `MAX_TOOL_ROUNDS` cap actually stopping an endless-tool-call loop) plus `tests/test_converse.py` updated to mock `agent_loop.run_turn` as a black box. (2) Manual end-to-end runs against the live Groq + Shopify dev store: asking for "milk" correctly triggered a brand-clarification question (Amul/Nandini/Mother Dairy) instead of guessing; naming a brand after that correctly resolved and added to cart; a multi-turn conversation built up a 2-item cart and `get_cart` reported the right running total; "check out my order" correctly read back the cart and total and asked for confirmation *without* calling `checkout(confirm=true)`; only after "yes, I confirm" did it call checkout and return a real Shopify checkout URL.

Notable non-bug found during testing: faster-whisper consistently mis-transcribed "Amul" as "Emil" (an Indian brand name outside Whisper's English-biased vocabulary) — the agent handled this gracefully (recognized "Emil" wasn't a real brand and re-asked) rather than adding the wrong thing, but it's a real STT accuracy limitation worth remembering for the Hinglish work in Week 3.

Not exhaustively tested by hand: the specific "retry once with corrected arguments" path (hard to force deterministically in a one-off conversation) and quantity/unit edge cases like "half a dozen eggs." Both are exactly what Milestone 2.3's eval suite is for — systematic scenario coverage instead of ad hoc manual conversations.

**Milestone 2.3 — Evals v1.** [x]
YAML scenarios + runner as specified in CLAUDE.md. 20 scenarios: happy paths, ambiguous items, quantity edge cases ("half a dozen eggs"), a checkout-without-confirmation trap the agent must not fall into. Wire into pytest.

Done 2026-07-25. `evals/fake_shopify.py` (in-memory catalog + cart backend, same function signatures as `mcp_commerce.shopify_client`), `evals/fake_mcp_client.py` (in-process fake MCP client — calls the real `mcp_commerce.server` tool functions directly via `list_tools()`, no subprocess needed), `evals/scenarios/*.yaml` (20 scenarios), `evals/runner.py` (loads scenarios, runs each through the real `agent_loop.run_turn`, scores tool selection/clarification/checkout-safety/final-cart-state, proactively throttles LLM calls 3s apart). `tests/test_evals.py` parametrizes pytest over all 20 scenarios, marked `@pytest.mark.eval` and excluded from the default `pytest` run (see `pytest.ini`) since they hit the live LLM and are slow/quota-consuming — run explicitly with `pytest -m eval` or `python -m evals.runner`.

Final result: **20/20 scenarios passing (100%)** against live Groq (`llama-3.3-70b-versatile`), Shopify mocked.

Real bugs found and fixed along the way (not just eval-writing — genuine agent/infra fixes):
1. Session-id leakage: the LLM was inventing placeholder `session` values (e.g. `"current_session"`) because `session` was exposed as a normal fillable tool parameter. Fixed by stripping `session` from the tool schemas shown to the LLM (`agent/mcp_client.py`'s `build_tool_schemas()`) and having `agent_loop.run_turn` auto-inject the real `session_id`.
2. Half-a-dozen-eggs quantity bug: agent added quantity=6 instead of 1 for "Eggs 6pc Tray." Fixed via a tightened system-prompt example (`agent/agent_loop.py`).
3. Bread brand ambiguity: agent silently narrowed its own search instead of asking, then treated the user's brand answer as an *additional* item instead of resolving the same request — ended up with two breads in the cart. Fixed via explicit "don't guess by re-searching, and a follow-up answer resolves the same request" prompt guidance.
4. Checkout-on-empty-cart: agent called `checkout(confirm=true)` on the very first message ("Check out my order.") without any prior confirmation exchange — worked correctly when the cart already had an item, only failed on an empty first-turn cart. Fixed via explicit "even on the first message, even if empty" prompt guidance.
5. Reliability bug in `agent/llm.py`: Groq/Llama-3.3 occasionally emits a malformed non-JSON function-call token (`<function=name{...}>`) instead of proper `tool_calls`, surfaced as a 400 `tool_use_failed` error — confirmed via direct API probing that this is inference noise (not deterministic on the prompt: identical requests sometimes fail every time, sometimes succeed at a later moment) and that a plain temperature=0 retry isn't reliable, but nudging the temperature up breaks the loop. Added a bounded retry with increasing temperature specifically for this error code, alongside the existing 429 retry.

One eval design correction: `remove_item_not_in_cart` originally asserted `remove_from_cart` must be called even for an item that was never added. The agent instead called `get_cart`, saw the item wasn't there, and answered correctly without calling `remove_from_cart` (there was no `product_id` to pass — nothing to remove). Rewrote the scenario to `forbid_tools: [remove_from_cart]` and tightened the prompt to make this flow (search → check cart → remove-or-explain) explicit and consistent, rather than forcing a pointless tool call.

Groq free-tier daily quota (100k TPD) was hit and fully recovered twice during this milestone (once mid-session on 2026-07-23, once again during verification) — a real constraint of the free tier, worked around by conserving quota (targeted scenario batches instead of full 20-scenario re-runs) rather than by creating additional accounts, which would violate Groq's terms.

Interview checkpoint: why MCP instead of direct function calls (swappable backend, standard contract), how you score an agent, what your pass rate was before/after prompt fixes, the session-id leakage bug and why tool schemas shouldn't expose infra-only parameters to the LLM, and the malformed-tool-call reliability story (inference noise vs. deterministic bug, and why the fix is a retry with varied sampling rather than a fixed backoff).

## Week 3 — Streaming, interruptions, Hinglish

**Milestone 3.1 — Streaming STT over WebSocket.** [x] Done 2026-08-17.
Switch /converse to a WebSocket session: client streams mic audio chunks, server runs VAD (silence detection) + incremental transcription.

Built 2026-07-25, see NOTES.md for full detail. `voice/vad.py` (webrtcvad-based `Endpointer`, frame-level end-pointing), `voice/pcm.py` (raw PCM -> WAV for faster-whisper), `agent/ws_stream.py` (new `/converse/stream` WS handler, kept `POST /converse` alongside it rather than replacing it), `agent/static/stream.html` (new streaming demo page, `ScriptProcessorNode`-based mic capture). "Incremental transcription" = VAD end-pointing (one transcribe call per finalized utterance), not live partial captions — faster-whisper has no true streaming decode mode; this was a deliberate, owner-confirmed scope call. 12 new tests pass (`test_vad.py`, `test_ws_stream.py`), plus a full live smoke test (real webrtcvad + real Groq + real Piper, no mocks) via a scripted WS client. **Not yet verified: the actual browser-side mic capture JS** — browser automation wasn't available this session, so the owner needs to click through `/stream` with a real mic before this checkbox flips to done.

**Update:** owner's live mic passes found five real bugs, all fixed, plus a scope decision — see NOTES.md. (1) Naive nearest-sample downsampling in `stream.html` was aliasing audio badly enough to break language detection. (2) An unhandled Groq API error silently killed the whole WebSocket session with no message to the client. (3) uvicorn's default WebSocket keepalive timeout (~40s) is shorter than this pipeline's documented worst-case latency (~45s) — **run command now requires `--ws-ping-interval 20 --ws-ping-timeout 90`**. (4) The Endpointer included the full trailing-silence tail in short utterances, and Whisper hallucinated boilerplate text ("Thank you.") for silence-dominated short clips — trimmed to ~240ms. (5) VAD `aggressiveness=2` was too lenient for real mic/room noise, causing a live utterance to run to the 30s safety cap instead of finalizing normally — raised to `aggressiveness=3`.

**Scope decision:** stopped relying on automatic VAD silence-detection as the *primary* end-of-utterance signal — it's inherently trial-and-error to tune for an arbitrary mic/room, and there's no guarantee a different setup doesn't surface another bug. Added a manual "Done talking" button (`{"type": "finalize"}` over the same WebSocket, `Endpointer.force_finalize()`) as the reliable primary control; VAD auto-detection still runs as a backup.

**(6) A turn hung 100+ seconds with zero CPU and no error** — `agent/llm.py`'s 429 retry honored any `Retry-After` value uncapped; heavy testing today likely approached Groq's daily quota. Fixed with `MAX_RETRY_DELAY_SECONDS = 15` (fail fast instead of blocking indefinitely); added `tests/test_llm.py`.

**(7) The auto-VAD "backup" was fighting the new button** — still finalizing on every ~1.2s mid-sentence pause *while the user was talking*, chopping speech into junk fragments before they could click "Done talking," and queuing a backlog that delayed the real reply. Fixed by raising `END_SILENCE_FRAMES` to ~9s — auto-VAD is now a rare fallback, not an active competitor.

**Paused 2026-07-25 ~15:29 — Groq free-tier rate limit exhausted.** Confirmed via server log: every turn attempt failing instantly with `429 Too Many Requests`, not a code bug (this session made a lot of live LLM calls debugging). Bug #6's fail-fast fix is confirmed working (fails in ~15s, not hanging). Owner chose to pause and wait for the quota to clear rather than push further blind fixes. Side observation to revisit on resume: a 28s utterance triggered a WebSocket 1011 (keepalive timeout) disconnect — long-clip STT time may need a bigger `--ws-ping-timeout` margin, not yet confirmed as a real issue since it's confounded with the rate-limit exhaustion.

**Resumed and closed out 2026-08-17.** Groq had deprecated `llama-3.3-70b-versatile` (2026-06-17, during the three-week pause) — every LLM call was failing with `404 model_not_found`, not a quota issue this time. Switched `LLM_MODEL` to Groq's official recommended replacement, `openai/gpt-oss-120b` (verified working, including tool calls, before touching the real server). Owner then ran the actual live browser/mic pass and found four more real bugs, all fixed this session (see NOTES.md for full detail): (8) VAD auto-finalizing on brief noise blips and Whisper hallucinating "Thank you." on the resulting silence-dominated clip — added a minimum-real-speech-content gate to `Endpointer`; (9) turn processing blocking the WebSocket receive loop, so audio spoken while a reply was being computed piled up and arrived late/out of order — decoupled frame-reading from turn-processing with a queue + background consumer task; (10) the LLM's markdown formatting (`**bold**`) being read aloud literally as "asterisk asterisk" — added a no-markdown instruction to the system prompt plus a defensive strip in `voice/tts.py`; (11) sustained non-speech noise (long enough to clear bug 8's fix) still producing hallucinated gibberish transcripts — added filtering on faster-whisper's own per-segment `no_speech_prob` confidence signal in `voice/stt.py`. All fixes covered by new/updated tests (`tests/test_vad.py`, `tests/test_stt.py`); full suite (44 tests) passing. Owner confirmed the live demo working end-to-end after all fixes.

**Milestone 3.2 — Barge-in.** [x] Done 2026-08-17.
If the user speaks while TTS audio is playing, stop playback, cancel the in-flight agent turn, process the new utterance. This is the hardest milestone in the project — budget a full session, possibly two.

Built: `voice/vad.py`'s `Endpointer` gained two public properties: `in_speech` (flips true after just ~90ms of speech — fast, but too trigger-happy to act on directly) and `speech_confirmed` (true only once `MIN_SPEECH_FRAMES` of real speech has accumulated — the same threshold that already fixed the short-utterance hallucination bug in Milestone 3.1). `agent/ws_stream.py` sends `{"type": "speech_started"}` on `speech_confirmed`'s False->True transition, available well before the utterance finishes — accept_frame's return value only fires on finalization, too late for this. Each finalized utterance's turn now runs as its own `asyncio.Task` (not a bare `await`) tracked in a small `_TurnState`, so a new `{"type": "barge_in"}` client message can cancel the currently-running turn and drain any other utterances still sitting in the processing queue — both without killing the consumer loop itself, which keeps listening for what comes next. `agent/static/stream.html` tracks whether reply audio is currently playing; on `speech_started` it only sends `barge_in` and stops playback if audio is *actually playing* right then. This condition matters: an early version sent `barge_in` on every utterance start regardless, which cancelled every turn the moment the next utterance began (since a turn's own 5-15s of processing is longer than a normal pause between sentences) — nothing ever got a reply. Restricting it to "only while genuinely playing" fixed it, matching the milestone's literal spec ("if the user speaks while TTS audio is playing").

Known, accepted limitation: cancelling an `asyncio.Task` only stops *our own code* from waiting on the result — a blocking call already handed to a background thread (the LLM HTTP request via `asyncio.to_thread` in `agent_loop.py`, or a Shopify tool call within it) keeps running to completion regardless, since Python can't forcibly kill a thread. If the cancelled turn had already called a mutating tool like `add_to_cart` before being interrupted, that mutation still applies for real — not undoable, but not dangerous either (nothing irreversible; `checkout` still has its own separate confirm gate). This is an inherent tradeoff of using threads for blocking I/O, not a bug to fix.

**Real bug found live (2026-08-17): the reply's own voice, played out loud through speakers, gets picked up by the mic and misclassified as the user interrupting** — self-triggering barge-in after just a word or two of the reply. Unlike the earlier noise-blip bugs, no speech-duration threshold can fix this: an acoustic echo of the assistant's own TTS output is genuine, continuous, natural-sounding speech, indistinguishable from a real interruption by duration alone — raising `MIN_SPEECH_FRAMES` further would only delay the false trigger, not prevent it, while equally delaying real interruptions. Mitigated (not fully solved) by adding explicit `echoCancellation`/`noiseSuppression`/`autoGainControl` constraints to `stream.html`'s `getUserMedia` call, and documenting headphones as the actually-reliable fix (no acoustic path from speaker to mic at all) directly on the demo page. Full acoustic echo cancellation for arbitrary local `<audio>` playback (as opposed to WebRTC call audio, where AEC is most reliable) is a genuinely hard problem without dedicated AEC infrastructure — real smart speakers solve this with far-field mic arrays and dedicated hardware, which is out of scope here. Worth being able to explain this distinction plainly if asked, rather than claiming it's fully solved.

**A third real bug, unrelated to barge-in mechanics but found during the same live pass: the very first utterance of a session came back transcribed entirely in Devanagari script** (clear English speech misdetected as Hindi). Root cause: `info.language_probability` was never checked — language auto-detect (intentionally on, per CLAUDE.md, for Hinglish) is least reliable on exactly the short/ambiguous audio where it matters most, and a wrong-language transcript can't match anything in the English product catalog. Fixed in `voice/stt.py`: when detection isn't confident (`language_probability < 0.6`) *and* the detected language isn't already English, retry once with English forced; a confident non-English detection (genuine Hindi/other speech) is left alone, so this only catches the ambiguous case. 4 new tests in `tests/test_stt.py` cover the retry, the non-retry (confident non-English), and the no-op (already English) paths.

Verified: `tests/test_vad.py` (2 new tests pin exactly when `in_speech`/`speech_confirmed` flip true/false), `tests/test_ws_stream.py` (updated 2 existing tests for the new `speech_started` message, added `test_barge_in_cancels_in_flight_turn_and_drops_queued_utterance`), `tests/test_stt.py` (4 new language-retry tests). Full suite: 52 tests passing. **Live-verified end-to-end by the owner**, including a real multi-turn conversation through checkout (search, clarification, add-to-cart, checkout link) with barge-in interruption working correctly and no further false triggers after the echo-cancellation and language-retry fixes.

**Milestone 3.3 — Hinglish.** [x] Done 2026-08-17.
Add 10 code-switched eval scenarios ("do packet doodh add karo"). Whisper's auto-detect handles a lot; fix the gaps with prompt guidance to the agent ("users may mix Hindi and English; item names may be in either"). Measure eval pass rate on the Hinglish set separately.

Built: 10 new scenarios, `evals/scenarios/21-30`, named with a `hinglish_` prefix in their `name:` field so `python -m evals.runner hinglish` reports their pass rate separately from the main English set — no runner code changes needed, the existing substring `name_filter` already supports this. Cover the same variety as the English set: simple add, quantity words, multi-item single turn, ambiguous brand (milk, bread), the dozen-eggs unit conversion, remove-without-respecifying-brand, read-only get_cart, and the checkout-confirmation trap.

Real gap found and fixed: the first full run scored 8/10, with both failures showing the identical shape — a Hindi quantity word ("do" = two) not making it into the tool call's `quantity` argument, defaulting to 1. Root cause diagnosed by inspecting the raw tool-call args directly (not just the pass/fail summary): "do" is genuinely ambiguous in Hindi — it's the number two, but also a common imperative particle ("kar do" = please do it, "daal do"/"de do" = put it in/give it), and both failing utterances used exactly that double-duty pattern ("do packet Maggi add kar do", "do doodh add karo" -> later "... daal do"). Added a targeted disambiguation instruction to `agent/agent_loop.py`'s `SYSTEM_PROMPT` (Hindi number-word glossary plus an explicit example of the two-"do"-in-one-sentence case); verified fixed via direct `agent_loop.run_turn` calls for both original failures before spending more eval-suite quota re-confirming.

One scenario (`hinglish_remove_without_respecifying_brand`) is flaky: passed on the very first run, failed twice in a row afterward with the same prompt, then passed again on a direct isolated retry. This matches the same non-deterministic inference-noise pattern already documented for this Groq model in Milestone 2.3 (`tool_use_failed` flakiness) — not a deterministic prompt gap, and not something to chase further with more prompt tweaks (risk of overfitting to noise). Best clean full-suite result after the quantity fix: **9/10 (90%)**, with the sole failure being this known-flaky scenario.

**Final confirmation run:** after switching to a fresh API key (same Groq account — confirmed with the owner this wasn't the previously-rejected multi-account workaround), 9 of 10 scenarios completed and **all 9 passed**, including `hinglish_remove_without_respecifying_brand` — its third pass out of four total attempts, confirming the two earlier failures were exactly the inference noise suspected, not a real gap. The 10th scenario (`hinglish_multi_turn_cart_building`) didn't complete — a 429 mid-run, the same account clearly under heavy quota pressure after this session's many live calls (5 full-or-partial runs plus several diagnostic one-offs). Not re-chased further: that scenario's simpler cousin (`multi_turn_cart_building`, its English equivalent) already passes reliably in the main eval suite, and every Hinglish scenario has now passed at least once with the fixes in place — this is solid, if not perfectly clean-single-run, evidence the milestone is done. Closing it out on that basis rather than continuing to burn quota chasing one final cosmetic 10/10.

## Week 4 — Ship it

**Milestone 4.1 — Docker.** [x] Done 2026-08-17.

2. **`agent/mcp_client.py`'s `connect()` never passed `env=` to `StdioServerParameters`.** The MCP SDK's `stdio_client` does *not* inherit the parent process's environment by default — it only passes a minimal safelist (`get_default_environment()`: `PATH`, `TEMP`, etc.), deliberately excluding app secrets. The `mcp_commerce.server` subprocess crashed with `KeyError: 'SHOPIFY_STORE_DOMAIN'`. This bug has existed since Milestone 2.1 and was invisible the entire project because the subprocess's own `load_dotenv()` call always happened to find a real `.env` file on disk locally, masking the fact that inherited env vars were never actually reaching it. It broke the moment that assumption stopped holding — a Docker image correctly excludes `.env` by design. Diagnosed by testing each layer in isolation directly inside the running container (raw `shopify_client` call → tool wrapper → full `MCPClient.call_tool` stdio round-trip) rather than guessing from the generic user-facing error message. Fixed by explicitly passing `env=dict(os.environ)`.
